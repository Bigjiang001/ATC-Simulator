# Qwen 中文播报耗时检查（2026-10-18）

本机 RTX 5080；PyTorch 2.11.0+cu128；Qwen3-TTS 0.6B CustomVoice，BF16，SDPA。检查的是中文播报，语音识别未调整。

## 实测

benchmark-qwen.py 固定文本、Vivian 音色及随机种子，直接调用模型，绕过 HTTP、浏览器与应用缓存。结果位于 local/.atc_logs/qwen-benchmark.log 与 qwen-benchmark-repeat.log。

| 场景 | 生成耗时 | 音频后处理 | 输出音频时长 |
| --- | ---: | ---: | ---: |
| 15 字短句，首次测量（含解码预热） | 14.159 秒 | 0.025 秒 | 3.04 秒 |
| 34 字长句，已预热，16 线程 | 15.740 秒 | 0.034 秒 | 7.41 秒 |
| 15 字短句，独立预热后交替复测 | 7.931–8.654 秒 | 0.010–0.028 秒 | 3.04 秒 |

短句交替复测中，4 线程为 8.577 / 8.564 秒，16 线程为 8.654 / 7.931 秒。没有稳定加速，所以未应用减少线程设置。测试在正常 Windows 桌面环境中进行，不能作为不同机器或 Mac 的严格性能对照。

## 原因与界限

1. 模型参数位于 cuda:0，主模型、talker 与 code predictor 的 attention 均为 SDPA；没有回退 CPU。
2. 主要时间是 Qwen 的逐步自回归语音代码生成；长句中约 15.676 秒用于该阶段，解码约 0.063 秒。变速处理不是瓶颈。
3. 当前 Qwen API 返回整段 WAV，前端等待完整响应和音频解码后播放，所以用户会先等待整句合成。前端还按顺序合成、播放各条通话，连续通话会继续排队。缓存仅能加速完全相同的文本、音色、语言及语速。
4. Mac 代码使用 MLX 8 位模型，Windows 使用 PyTorch BF16，推理方式不同；没有同一 Mac 的实测数据，无法证明 Windows 系统自身导致了具体多少性能损失。
5. 日志中的缺少独立 flash-attn 提示不代表没有 GPU 注意力：当前实际使用 SDPA。不能只凭此提示认定需要重装 Windows 或安装 flash-attn。non_streaming_mode=False 也不会把现有 WAV HTTP 接口变成真正流式播放。

本次保留模型、音色、采样与语音识别行为，新增 Qwen 生成、变速、音频时长与总耗时日志。下次重新启动服务生效。真正减少开口等待需要同时改造支持增量音频的推理路径和流式传输/播放，或采用经验证的更快推理实现；不能承诺通过改一项启动参数达到实时播报。
